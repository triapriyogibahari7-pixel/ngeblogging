# Durable installation claim foundation

This commit defines a private ledger and service-role-only claim RPC plus an acknowledgement parser. It does not apply SQL, call the RPC, expose a route, connect a dispatcher, mutate site_domains/sites, change DNS/routing or enable any runtime flag. The backend evidence reader remains read-only and is not write authorization.

The RPC derives user, site and domain from production records rather than caller-supplied identity. Its intended transaction locks the order, registration job and current site owner as needed, checks paid/registered state, persisted verified payment event, quote and registration evidence, destination binding and mapping conflicts, then records at most one ledger row per order/domain. Existing claims retain their ID and are reconciliation-only, not permission for another provider write. There is no automatic expiration, release or retargeting after uncertain effects.

The unique domain reservation serializes participants in this NEW claim protocol only. Existing manual domain writers do not automatically acquire this advisory lock or honor this table. A later mapping transaction and provider-operation protocol must handle those writers, revalidate current ownership/payment/evidence, reserve the actual mapping safely and reconcile ambiguous external effects. Site ownership can change after the claim transaction. Do not treat claimed state as installation success or reuse a stale plan to overwrite another site's mapping.

No UPDATE/DELETE grant is added to the new ledger for service_role; no completion/release transition is implemented here. installed is a reserved future ledger state, not a state this RPC creates or independently certifies. All acknowledgements keep provider_mutation_allowed, installation_action_taken and installation_confirmed false. service_role remains a trusted backend role, not an untrusted client identity.

Ten candidate parser tests passed locally on Node v20.20.1. They do NOT execute this migration or prove PostgreSQL locks, privileges, atomicity or concurrent behavior. Before application, verify real schema types, row-lock privileges, same-order/domain concurrency, refund/owner changes, existing manual flows and migration ordering in isolated PostgreSQL. Then validate the supported Node >=22.12.0 build and implement the dispatcher/provider-observation stages. Production remains unchanged.
