# SaaS migration executor core — not production wired

This module implements prepare, cutover, rollback and authorized status dispatch through required server-side journal/provider/records adapters. It is not another canExecute:false preflight model: it invokes staged provider mutations, traffic switching, conditional database commit and compensating restore operations when explicitly enabled. However concrete Cloudflare, transactional database/durable journal adapters and an authenticated HTTP/operator integration are NOT included or configured by this commit. Do not enable the customer migration button, claim any domain migrated, or deploy as a complete migration service. Existing preflight/staging notes remain applicable to the unconnected production UI.

All mutation switches default false; prepare, cutover and rollback have independent switches so rollback need not be disabled with a prepare/cutover kill switch. Input actor/site/domain/migration IDs must be canonical UUIDs. authorize must derive actor identity from a verified server session, re-check current owner/admin authority and enforce an operational maintenance lock covering other domain writers, cron and repair scripts. It must not trust actorId or permission booleans supplied by a customer. No endpoint exposes this internal module yet.

## Required adapter guarantees

Journal: acquire/assertHeld/read/write/release must use a durable, cross-instance exclusive per-domain lock and fenced version compare-and-set. write must reject stale versions and identity/snapshot substitutions. No lock timeout may automatically permit a competing writer while a previous provider operation may still complete. Journal snapshots and audit events are server-only; never persist API tokens or client credentials. In-memory fixtures are TESTS ONLY.

Records: read returns {domain,site} with an authoritative complete domain row and the site identity/custom_domain value. assertUnchanged compares the complete expected snapshot. commit and rollback MUST re-authorize and implement atomic database transactions, row locking and compare-and-set internally; an earlier separate assert is not sufficient. Preserve domain/site identity, primary selection, created/verified timestamps and alias hostname/enabled semantics. Commit binds the apex to its exact staged SaaS ID; rollback preserves the original full-zone ID and uses actual restored binding/certificate IDs, never stale guessed IDs. Integrate legacy SaaS refresh/alias metadata handling before production so a later refresh cannot discard preserved aliases.

Provider: inspectSource must authoritatively verify source zone/account, configured SaaS zone/fallback/target, apex capability, complete apex/alias inventory, disabled aliases, maintenance ownership and a restorable DNS/Worker/certificate snapshot. Required evidence includes inventoryComplete, rollbackVerified, platformVerified, maintenanceHeld, apexCapabilityVerified and an explicit trafficMayChangeDuringPrepare boolean. These booleans are trusted adapter attestations, NOT customer inputs. stage uses migrationId as a durable per-host idempotency key; inspectTarget must verify exact staged IDs, ownership metadata and active hostname plus active TLS for every host. Every composite provider operation needs durable per-API-call intents/checkpoints and bounded, settled/cancellable operations. Do not wrap unresolved writes in a timeout Promise.race and then unlock.

Cloudflare documents that pre-validation is unsupported for Orange-to-Orange hostnames already on Cloudflare, and activating such a hostname immediately routes traffic through the SaaS zone. Treat prepare as potentially traffic-changing and obtain explicit scope-specific acknowledgement before stage. This core does not promise zero downtime or that all validation models work for O2O. Reference: https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/domain-support/hostname-validation/pre-validation/

Target proof must independently verify authoritative DNS, actual SaaS routing/provider IDs, valid TLS and correct site content for EVERY scoped hostname. It must bind siteId/migrationId, be no older than 60 seconds and not merely show that the old route still serves the right website. Rollback proof must verify the restored original provider/Worker route, TLS and site, not just an HTTP 200 from the remaining SaaS route. Do not claim proof from flags, database status or certificate IDs alone.

## Execution and recovery

Prepare snapshots source and journals intent before staging. Cutover requires active per-host target/TLS, switches scoped traffic, checks fresh live proof, then commits the database conditionally without selecting a new primary. Rollback restores source configuration and certificate readiness before removing ONLY migration-owned SaaS resources, verifies restored traffic, then conditionally restores the record. Never delete source zones, change NS/DS/DNSSEC, disable aliases, remove unrelated provider resources or overwrite intervening edits. Any such additional operation needs its own reviewed plan/approval.

An error after a mutation starts is deliberately treated as uncertain, journals needs_recovery where possible and retains the lock. There is no blind automatic retry or rollback: a database commit timeout may already have committed. Operators must first settle/reconcile provider and database outcomes, preserve checkpoints and explicitly repair the durable journal/lock before resuming. Crash recovery and releasing a stuck lock require a production adapter/operator procedure; they are not implemented by the in-memory tests.

Twenty-five state-machine tests passed locally on Node v20.20.1 using simulated in-memory journal, provider and database adapters. They cover phase order, idempotence, authorization, traffic acknowledgement, maintenance/apex/inventory checks, provider identity, TLS/live proof, compare-and-set conflicts, concurrent duplicate requests, unknown outcomes and rollback ordering. No real CF/database/DNS changes, Node 22.12.0/full build/native Worker/browser validation, GitHub CI, live cutover or production rollback has been performed. Production integration is still pending.
