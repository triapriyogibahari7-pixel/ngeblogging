# Internal installation reservation coordinator

preparePaidDomainInstallation connects the committed evidence reader, planner and claim parser. It is not mounted as a public endpoint or wired into runtime scheduling/provider dispatch in this commit. Both DOMAIN_INSTALLATION_PREFLIGHT_ENABLED and DOMAIN_INSTALLATION_CLAIM_ENABLED must be exactly true, with production order environment. No flags are activated here. Never expose this service-role coordinator to unauthenticated browser callers.

The coordinator checks evidence, calls exactly one fixed claim RPC for the same order ID, validates the acknowledgement, and checks evidence again. Its overall deadline covers both reads and claim. It makes no site mapping, registrar, zone, DNS, Worker-routing, payment or refund call. A successful fresh reservation can require 20 GETs plus one POST; include this in future Worker subrequest/time budgets.

claimOutcome distinguishes not_attempted, rejected, unknown and recorded. Lost/malformed/redirected/oversized claim responses remain unknown and reconciliation-only; a reservation may already exist. There is no automatic POST retry, new random claim ID, release, alternate target or fallback. A separate invocation with the same order relies on the persistent RPC idempotency contract and must validate its reused acknowledgement. Post-claim evidence changes retain the validated claim but block readiness. No raw upstream errors or arbitrary SQL error strings are returned.

Even ok=true is reservation readiness only, not an atomic read snapshot, proof of real SQL durability, provider-write authorization or installation confirmation. All results keep newClaimAllowed, providerMutationAllowed, installationStarted and installationConfirmed false. Ownership/payment/evidence may change after the last read. A future mapping/provider protocol must revalidate the claim and current records, handle legacy manual writers and reconcile ambiguous external effects before reporting active installation.

Eleven candidate tests passed locally on Node v20.20.1 with three SHA-matched committed dependencies. All database responses and the claim RPC were mocked; no real ledger row was created. These tests do not prove live SQL, row-lock privileges, concurrency, supported Node >=22.12.0 build, React behavior, Worker scheduling or provider permission. Production migrations, schema verification and coordinated activation remain separate release gates.
